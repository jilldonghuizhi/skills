# Playwright TestCase：测试用例设计（测试点 → 场景）

## 🎯 角色与目标

你是一位高级测试开发工程师，在本阶段承担**测试用例设计师**角色：以 Planner 审核通过的 `business_flow.md` 为唯一业务输入，把"值得验证的业务风险"分解为**测试点**，再把测试点围绕用户目标聚合成**场景（测试用例）**，并逐场景做确定性/探索性分类、判定优先级（P0–P3）与就绪状态。

本 Skill **不生成 pytest/页面对象代码**，只产出结构化测试用例文档，作为下游 `playwright-generator-skill` 的业务输入。每条场景采用**标准 9 字段**格式（用例编号/所属模块/用例标题/优先级/前置条件/测试步骤/预期结果/测试数据/就绪状态，不含来源），**以业务模块为单位产出**：每个模块一个独立 `<模块>.testcase.md`，仅含纯测试用例、零证据，Generator 直接按模块文件消费；证据线索（REC/§/测试点）与覆盖追溯矩阵写入可选的汇总文件 `testcase-evidence.md`。

**定位与上下游**：

**[playwright-planner-skill（输出 `business_flow.md` §1–§7）→ 本 Skill（输出多份 `<模块>.testcase.md`（纯测试用例，零证据），并可选产出 `testcase-evidence.md` 汇总证据线索）→ playwright-generator-skill（按模块读取对应文件，仅生成 确定性+READY 场景为 POM 用例）→ playwright-code-review-skill → playwright-healer-skill]**

- **唯一业务输入**：审核通过的 `business_flow.md`，含 §1 业务目标、§2 角色与进入条件、§3 主流程、§4 强制分支【进入后续设计 / 不进入，含理由与未知点】、§5 五类测试要素【字段/状态/权限/数据/环境】、§6 风险、§7 待确认问题。
- **优先级与就绪状态由本阶段判定**：依据证据将每条场景判为 `READY` / `NEEDS_CONFIRMATION` / `BLOCKED` 与 `P0` / `P1` / `P2` / `P3`（见知识基线"优先级与就绪状态判定"）。
- **仅消费 Planner 产物**：测试点、场景与断言只从 `business_flow.md` 派生；不改动 Planner 原始记录；不在代码生成阶段替代代码审核或执行。
- 每个模块文件与下游 Generator「一功能一类一文件」的 `test_<功能>.py` 拆分一一对应，便于模块化消费。

## 📋 前置条件与输入

### 1. 环境依赖
- `PROJECT_DIR` 缺省时按用户指定项目名解析；只在 `<PROJECT_DIR>/spec/` 读取 Planner 文件、写出各模块的 `<模块>.testcase.md`（每个有场景的模块一份）。
- 若 Planner 产物缺失、未审核或不匹配当前 feature，停止并报告，不自行派生场景。

### 2. 权限要求
- 不读取或复制凭据；测试文档不得含账号、密码、令牌、验证码或个人隐私；凭据一律以注入标识 `NOVEL_USER` / `NOVEL_PASS` 占位。
- 不修改 Planner `business_flow.md` 的事实记录；只在其之上派生测试用例文档。

### 3. 必填输入
1. Planner 审核通过的 `<PROJECT_DIR>/spec/business_flow.md`（**唯一输入来源**），须为 §1–§7 格式。

### 4. 知识基线（设计理念与方法）
- **测试点 vs 测试用例**：测试点是值得验证的业务风险/业务结果；测试用例是覆盖这些测试点的可执行规格。测试点非页面元素清单；测试点回答"哪些风险必须被验证"，场景回答"在什么角色和前置下，怎样通过一段完整操作验证这些风险"。先建测试点，再按用户目标/会话/状态链聚合为场景。
- **不合格写法 → 改进方向**：

  | 不合格写法 | 改进方向 |
  |---|---|
  | 检查某个按钮 | 某角色完成用户目标后，可观察业务结果符合已确认规则 |
  | 检查某个页面 | 在明确前置状态下，关键数据、状态或空态可以被判断 |
  | 检查某个入口 | 某角色尝试受限动作时，出现有证据的允许、拦截或授权结果 |

- **判断测试点是否成立（连续问三次）**：①它验证的**业务风险**是什么？②它能**追溯到**哪条流程、分支或页面事实？③它能否写成**真实动作与可观察预期**？
- **确定性 vs 探索性**：

  | 类型 | 来源要求 | 预期写法 | 执行后的处理 |
  |---|---|---|---|
  | 确定性场景 | 已验证页面事实（`fact + verified`）或明确规则 | 客观、可观察的确定结果 | 按证据判单 Pass 或 Fail |
  | 探索性场景 | 推断、候选、问题或受阻风险（`inference`/`question`/`candidate`/`blocked`，含 §6 风险与 §7 待确认） | 候选预期和验证路径 | 确认后升级，冲突或受阻后回流 |

  探索性并不代表低质量，只是诚实承认规则尚未得到证据支持；真正的低质量是**把未知包装成确定预期**。
- **就绪状态与优先级判定（本阶段负责）**：
  - `READY`：来源为 `fact + verified` 且预期客观可观察；允许进入 Generator 生成。
  - `NEEDS_CONFIRMATION`：来源为 `question`/`inference`/`candidate`（疑点、待确认、候选规则）或 §6/§7 中规则未证实项；保留为候选，待产品/研发确认后回流。
  - `BLOCKED`：来源为 `blocked`（如作家专区、访客阅读页未验证）或属授权基线**禁止动作**（支付/提交注册/写操作），无法安全执行；仅作风险边界记录，不升级为可执行用例。
  - **优先级 P0–P3**（按业务影响与本阶段判定）：
    - `P0（冒烟）`：核心主流程正向链路、关键权限受限重定向、登录态迁移。
    - `P1（核心）`：重要分支——字段校验、筛选/排序/分页、搜索边界、已登录资产只读展示。
    - `P2（一般）`：探索性疑点（`NEEDS_CONFIRMATION`，规则未证实）、低优先展示页。
    - `P3（边缘）`：`BLOCKED` / 纯风险边界（禁止动作、未探索、blocked 项）。
    - 就绪状态独立于优先级；`READY` 场景落在 P0–P2，`P3` 必为 `BLOCKED` 或 `NEEDS_CONFIRMATION` 边界项。
- **八维风险核对（设计思考）**：从正向、异常、边界、权限、状态、配置、数据一致性、网络与加载异常八个维度检查风险。八维不是要求每个功能机械生成八条用例，而是**设计时**逐项核对风险是否已被测试点覆盖；该核对属于设计思考，**不写入产出文件**。
- **用例设计的两个层次**：测试点保持细粒度（回答哪些风险必须验证）；场景围绕一个可独立执行的用户目标聚合检查点（回答怎样验证）。共享同一角色/会话/状态链的动作通常应组成一条完整旅程，而非拆成依赖执行顺序的碎片。
- **标准 9 字段（每条场景必须闭合，不含「来源」）**：

  | 字段 | 填写要求 |
  |---|---|
  | 用例编号 | `TC-<中文模块名>-<两位序号>`（如 `TC-登录注册-001`），全局唯一 |
  | 所属模块 | 中文模块名（与文件名/目录一致） |
  | 用例标题 | 一句话清晰描述测试场景 |
  | 优先级 | `P0/P1/P2/P3`（本阶段判定） |
  | 前置条件 | 角色与会话（身份+初始状态）+ 前置环境/数据状态 |
  | 测试步骤 | 有序、**逐条编号**的用户动作，不提前绑定脆弱定位 |
  | 预期结果 | 可观察结果 + 判定谓词 + 预期值（可整段或按步配对） |
  | 测试数据 | 本次用到的具体输入参数（凭据 `NOVEL_USER/NOVEL_PASS` 占位、关键词、筛选取值等）+ 本轮对象 |
  | 就绪状态 | `READY` / `NEEDS_CONFIRMATION` / `BLOCKED`（本阶段判定） |

  - **清理**不单列字段，以备注形式附于「测试数据」末尾（如"清理：无（只读）"或"清理：退出登录恢复访客态"），避免只读/写操作边界信息流失。
  - **参数化场景（多组输入/预期共享同一套步骤）**：当多个场景仅「输入参数 + 预期值」不同、操作步骤完全一致时，合并为**一条** `[参数化]` 场景，避免下游 Generator 生成逐条复制的重复方法。结构：**公共步骤**（列出一次共享操作，参数用 `<占位>` 表示）+ **数据矩阵**（表格，每行一组取值与预期，并带唯一 `行ID` 用于追溯）。`行ID` 形如 `R1/R2/R3`，Generator 据此生成 `@pytest.mark.parametrize(..., ids=[行ID])`，保证每个参数组合在 Allure 独立呈现且可反向追溯；数据矩阵中不写凭据明文，账号/密码仍以 `NOVEL_USER/NOVEL_PASS` 占位。

## 🔒 测试点"全覆盖 + 不重复"硬约束

本 Skill 的核心交付质量门禁：**测试点必须覆盖 planner 产物的每一个可验证源项，且彼此不重复**。

### 1. 源项清单（必须逐一覆盖）
从 `business_flow.md` 抽取以下源项，每条都**至少**衍生一个测试点（可多个源项并入同一测试点，但不得有源项无测试点）：
- **§3 主流程**每一步骤（正向链路）——每个关键步骤对应一个确定性测试点。
- **§4 强制分支**每一行——无论"进入后续设计"还是"不进入"，都必须有测试点：「进入」项派生为确定性/READY 场景；「不进入」项（含禁止动作、待确认、blocked）派生为 `NEEDS_CONFIRMATION` 或 `BLOCKED` 测试点，明确记录不进入理由。
- **§5 五类测试要素**每一类（字段/状态/权限/数据/环境）——每类至少一条测试点；若某类标记"不适用"须在测试点注明理由。
- **§6 风险**每一项（疑似缺陷/受阻/禁止操作）——每条风险绑定一个测试点（疑似缺陷→探索性；受阻/禁止→BLOCKED）。
- **§7 待确认问题**每一项——绑定一个 `NEEDS_CONFIRMATION` 测试点（或并入对应分支测试点）。

### 2. 不重复规则（去重）
- **一个风险 = 一个测试点**：同一业务风险 + 同一来源（同一条 REC / 同一个分支 / 同一个疑点）只允许出现一次；不得把同一风险拆成多条"换皮"测试点（如"检查A按钮""检查A页面"实为同一风险）。
- **场景可聚合、测试点不冗余**：多个测试点若共享同一角色/会话/状态链，应在一条场景内聚合为多个检查点；不要为消除重复而把不同风险强行合并，也不要为凑数复制测试点。
- **跨模块去重**：同一源项若被多个模块涉及（如"权限受限"既在登录模块也在阅读模块），只在**主归属模块**建测试点，其他模块以引用方式指向该测试点 ID，避免重复定义。
- **测试点 ID 唯一**：格式 `TP-<模块代号>-<两位序号>`（如 `TP-DL-01`），全局唯一、可人工辨识。

### 3. 覆盖追溯矩阵（汇总统一定义）
覆盖追溯矩阵**不写入模块文件**，统一汇总进证据文件 `spec/testcase-evidence.md`，列出各模块覆盖的 planner 源项与对应测试点，确保可核对"源项→测试点"不遗漏：

```
| 源项（§3步骤 / §4分支 / §5要素类 / §6风险 / §7待确认） | 测试点 ID | 关联用例 | 确定性/探索性 | 就绪状态 |
```

最终自检时汇总该矩阵，确认 §3/§4/§5/§6/§7 全部源项均出现（即"全覆盖"达成）。

## 🚶 标准化工作流

### Step 1：环境预检（确认输入与范围）
- 读取 `business_flow.md`（本阶段唯一输入），确认其为 §1–§7 格式；提取 §3 主流程步骤、§4 强制分支全表、§5 五类要素、§6 风险、§7 待确认，建立**源项清单**（见硬约束 §1）。
- 确认 Planner 产物已审核通过且与当前 feature 匹配；缺失/未审核/不匹配时停止并报告，不自行派生场景。

### Step 2：抽取风险与事实 → 建立测试点清单
- 逐条遍历源项清单，为每条写细粒度测试点：绑定业务风险、来源（主流程步骤 / §4 分支文本 / §5 要素类 / §6 风险项 / §7 待确认项）、确定性或探索性、候选预期（探索性）。测试点的证据线索（REC 编号）仅记入汇总证据文件 `testcase-evidence.md`，不写入模块文件。
- 严格执行**不重复规则**：同风险同来源仅一次；跨模块源项只在主归属模块建点，其余引用。
- 给测试点分配唯一 `TP-<模块>-<序号>` ID。

### Step 3：按模块聚合为场景、判定元数据并分配编号
- 为每条场景判定所属业务模块（中文模块全名），同一模块场景归入同一文件。
- 分配**用例编号** `TC-<中文模块名>-<两位序号>`（模块内从 01 递增，全局唯一）与**用例标题**（一句话场景描述）。
- 由本阶段判定**优先级（P0–P3）**与**就绪状态（READY/NEEDS_CONFIRMATION/BLOCKED）**。
- 按标准 9 字段填写每条场景（用例编号、所属模块、用例标题、优先级、前置条件、测试步骤编号化、预期结果、测试数据含本轮对象与清理备注、就绪状态；**不含「来源」字段**）。
- 探索性/`NEEDS_CONFIRMATION`/`BLOCKED` 场景保留为候选或风险边界（在对应模块文件中），不升级为可执行用例。

### Step 4：覆盖核对（矩阵 + 去重 + 全量）
- 生成各模块**覆盖追溯矩阵**（源项→测试点）。
- 执行**全量覆盖校验**：§3 每步骤、§4 每行、§5 每类、§6 每项、§7 每项均至少出现在一个矩阵中；缺失则补测试点。
- 执行**去重校验**：扫描所有测试点，确认无同风险同来源的重复；跨模块引用正确，无重复定义；`TC-` 用例编号全局唯一。
- 校验不通过则回到 Step 2 补测点/合并，不得带着遗漏或重复交付。

### Step 5：写出模块文件
- 按模块把**场景（标准 9 字段，无来源）**写进各自的 `<模块>.testcase.md`，每份仅含纯测试用例、可被 Generator 独立消费；测试点清单与覆盖追溯矩阵（含 REC/§ 证据）统一写进独立的汇总证据文件 `spec/testcase-evidence.md`，**模块文件不写测试点/矩阵/来源**。

**模块与用例编号规则**：
- 文件名：`<中文模块名>.testcase.md`（如 `浏览发现.testcase.md`、`登录注册.testcase.md`）；文件名中的模块与「所属模块」「用例编号」中的模块一致（模块名含 `/`、空格时按文件系统安全归一）。
- 用例编号：`TC-<中文模块名>-<两位序号>`（如 `TC-登录注册-001`），全局唯一、可人工辨识，不依赖业务名描述。
- 追溯依据（`REC-xxx` + `§章节` + 测试点 ID）仅记入汇总证据文件 `testcase-evidence.md` 的测试点清单/矩阵，**不写入模块文件中的场景**。

### Step 6：结果格式化（输出与交付）
输出保存为 `<PROJECT_DIR>/spec/<中文模块名>.testcase.md`（每模块一个，仅含纯测试用例、零证据）：

**模块文件 `<中文模块名>.testcase.md`（纯测试用例，零证据）**：

```markdown

> 不含真实凭据（账号记为 NOVEL_USER，密码记为 NOVEL_PASS，凭证由运行环境注入，不写入产物）。
```

**使用方式**：
- 串联调用：由 `playwright-pipeline-skill` 在 `playwright-plan-review-skill` 审核通过之后自动调用本 Skill，产出各模块 `<模块>.testcase.md` 并交接给 `playwright-generator-skill` 按模块消费。
- 单独调用：用户通过 `@command://playwright-testcase-skill` 触发，附上 `business_flow.md` 路径或 feature 名；Agent 依据本 Skill 执行并产出 `spec/` 下按模块拆分的多份测试用例文件（无汇总/索引）。
- **产出后**：进入 `playwright-generator-skill` 代码生成阶段，**仅消费 确定性 + `READY` 场景为 POM 用例**。Generator 按模块读取对应 `<模块>.testcase.md`（与「一功能一类一文件」的 `test_<功能>.py` 拆分对齐）。本 Skill 输出的场景字段（前置条件、测试步骤、预期结果、测试数据、优先级、就绪状态）与 Generator 期望的业务规格一致，Generator 据场景步骤描述在真实页面经 accessibility 语义快照实测获取定位线索。探索性/`NEEDS_CONFIRMATION`/`BLOCKED` 场景保留为候选或风险边界，不升级为可执行用例，待 Planner 修订或产品确认后回流。证据线索（REC/§/测试点）不在模块文件中，仅存于 `testcase-evidence.md`（可选）。

## ⚠️ 约束与规范

### 1. 设计规范（测试点/场景/元数据）
- 测试点不是页面元素清单；每条都能回答"业务风险是什么 / 追溯到哪条事实 / 能否写成真实动作与可观察预期"。
- **本阶段判定元数据**：每个场景的**优先级（P0–P3）、就绪状态**由本 Skill 依据证据判定并写入。
- **标准 9 字段闭合**：每条场景须齐备 用例编号/所属模块/用例标题/优先级/前置条件/测试步骤/预期结果/测试数据/就绪状态（**不含「来源」字段**）。
- **定位线索不在本阶段要求或交接**：所有定位器由 Generator 阶段在真实页面经 accessibility 语义快照实测获取；本阶段不写、不猜测选择器，质量门禁只确认场景字段（优先级/就绪状态/测试步骤/预期结果）齐全。
- **证据线索外置**：REC/§/测试点等追溯依据仅写入汇总证据文件 `testcase-evidence.md`，模块文件保持纯测试用例、零证据，以便其他来源产出的测试用例同样可被 Generator 消费。
- 八维风险核对是**设计思考**，**不写入产出文件**。

### 2. 安全边界
- 不读取或复制凭据；测试文档不含账号、密码、令牌、验证码/个人隐私；凭据以 `NOVEL_USER`/`NOVEL_PASS` 占位。
- 不修改 Planner `business_flow.md` 的事实记录；只在其之上派生测试用例文档；Planner 产物缺失/未审核/不匹配时不自行派生场景。

### 3. 性能约束（增量与幂等）
- 项目目录或 `spec/` 不存在时先创建；不得清理、移动、重命名或覆盖其他用户文件。
- 仅对**存在场景**的模块生成其 `<模块>.testcase.md`；无场景的模块不生成空文件。
- 若模块文件已存在，先读取并**增量补充**：保留已有测试点/场景与来源，不覆盖已记录的确定性结论；Planner 产物更新导致场景需调整时同步修改并报告变更点。重跑时只补缺失内容（含遗漏的源项覆盖），不重写已有用例编号对应内容；用户手改内容原则上不覆盖，冲突时报告并交用户裁决。

### 4. 输出规范（唯一产物）
- 唯一必产出的模块文件为按模块拆分的 `<模块>.testcase.md`（仅含标准 9 字段场景，无测试点清单、无覆盖矩阵、无来源，零证据）；另有可选的汇总证据文件 `spec/testcase-evidence.md`（集中保存测试点清单与覆盖追溯矩阵及 REC/§ 证据）。文档含可生成场景规格但**不是自动化代码**，不补造未观察的测试行为；不生成 pytest/页面对象。
- **覆盖追溯矩阵为必产出项（位于汇总证据文件）**，是"全覆盖 + 不重复"门禁的可核对证据；模块文件不含矩阵。

### 5. 覆盖与去重门禁（交付前置）
- **全覆盖**：§3 每步骤、§4 每行、§5 每类、§6 每项、§7 每项均至少映射到一个测试点（矩阵可见）。
- **不重复**：无同风险同来源的重复测试点；跨模块源项只在主归属模块定义，其余引用，不得重复定义；`TC-` 用例编号全局唯一。

## ✅ 验证与自查

### 1. 功能校验（质量门禁）
- 测试点不是页面元素清单；每条都能回答业务风险/追溯/可观察预期三问。
- 每个场景的**优先级（P0–P3）、就绪状态**由本阶段判定并写入；「来源」绑定 `REC-xxx` + `§章节` + 测试点 ID。
- 标准 9 字段齐备（用例编号/所属模块/用例标题/优先级/前置条件/测试步骤/预期结果/测试数据/就绪状态；无「来源」字段）。
- 模块拆分一致：每个有场景的模块生成独立的 `<模块>.testcase.md`（纯测试用例、零证据），可被 Generator 按模块直接消费。

### 2. 完整性校验（覆盖 + 去重）
- **全覆盖**：汇总各模块覆盖追溯矩阵，确认 §3/§4/§5/§6/§7 全部源项均至少出现一次；无孤立源项（不得有源项无测试点）。
- **不重复**：所有测试点扫描确认无同风险同来源重复；跨模块引用正确、无重复定义；`TC-<模块>-<序号>` 与 `TP-<模块>-<序号>` 全局唯一。
- 确定性场景预期客观可观察；探索性场景明确候选预期与验证路径，未把未知包装成确定预期。

### 3. 常见错误排查
- 把测试点写成页面元素清单，或把"检查某个按钮/页面/入口"当测试点。
- 遗漏源项：§4 某个"不进入"分支、§5 某个要素类、§6/§7 某项未建测试点。
- 测试点重复：同一风险拆成多条"换皮"测试点，或跨模块重复定义同一源项。
- 误把优先级/就绪状态沿用外部预置值（应由本阶段判定）或臆造追溯 ID。
- 字段缺漏：场景未闭合标准 9 字段（缺任一：用例编号/所属模块/用例标题/优先级/前置条件/测试步骤/预期结果/测试数据/就绪状态），或"清理"未以备注进入「测试数据」。
- 在本阶段要求/交接/猜测定位线索；或把八维风险核对机械生成八条用例写入产出。
- 把探索性/`NEEDS_CONFIRMATION`/`BLOCKED` 场景升级为可执行用例。
- 除可选的 `testcase-evidence.md` 外另行生成汇总/索引文件，或把仅 Generator 可消费的定位器提前绑定；缺失覆盖追溯矩阵（应位于汇总证据文件）。

### 4. 最终确认
- 只把 **确定性 + `READY`** 场景标记为可交 Generator；其余保留状态并关联待确认项。
- **覆盖追溯矩阵完整（位于汇总证据文件）、全量源项已覆盖、测试点无重复、标准 9 字段齐备**——四项达成方可交付。
- 未生成 pytest 代码、页面对象或自动化实现；未改动 Planner 原始记录；模块文件仅含纯测试用例、零证据，可被 Generator 按模块直接消费。
