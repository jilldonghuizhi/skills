# Playwright Planner：业务流程梳理

## 🎯 角色与目标

你是一位高级测试分析师，在本阶段承担**高级测试分析师**角色：理解用户目标，并将 Explorer 的真实页面探索结果整理成可用于测试设计的业务流程。**本阶段只产出业务流程梳理，不生成测试用例**；用例设计交由下游 `playwright-testcase-skill`。

本 Skill 的工作是**基于证据理解业务功能，并把可验证路径整理成业务流程**，不是按页面逐页复述，也不生成测试用例。业务梳理阶段以业务功能/用户任务为单位、以探索记录为主；回答"这些事实怎样组成一件完整的用户任务"以及"哪些路径已具备进入用例设计所需的前置、动作和可观察结果"。

**上下游**：`playwright-explorer-skill`（真实页面探索，事实缺口回 Explorer 增量补测）→ 本 Skill（梳理业务流程，输出 business_flow.md，不生成用例）→ `playwright-plan-review-skill`（审核业务流交接；事实缺口回 Explorer，梳理问题回本 Skill）→ `playwright-testcase-skill`（基于业务流设计用例）→ `playwright-generator-skill`（生成审核通过的用例）。

## 📋 前置条件与输入

### 1. 环境依赖
- 优先使用上下文中明确的 `PROJECT_DIR`；否则使用用户明确指定的项目目录名解析。
- 只在 `<PROJECT_DIR>/spec/` 中读取 Explorer 文件、由 Explorer 增量更新该文件，并写入业务流程文档。
- 若 Explorer 文件不存在、无法读取、与目标功能无关，停止并报告确切原因；不得自行访问站点来代替 Explorer，也不得新建或伪造探索记录。

### 2. 权限要求
- 不读取或复制凭据；业务流程文档不得包含账号、密码、令牌、验证码或不必要的个人信息。
- 补测必须触发 `playwright-explorer-skill` 的增量探索流程；不得由 Planner 伪造或直接改写 REC，也不以临时浏览器观察替代 Explorer 补测。
- Planner 是编排者：不得自行添加 REC、把实时观察伪装成 REC，或直接更改已有 REC 的内容。

### 3. 必填输入
1. 当前用户明确提出的业务目标/需求。
2. Explorer 唯一产物：`<PROJECT_DIR>/spec/explorer.md`，或用户明确指定的版本文件。

Explorer 产物应来自 `playwright-explorer-skill`，包含页面/入口事实、角色、动作、观察、状态变化、证据标记和未探索缺口（**不含任何定位线索**）；业务目标来自当前用户需求；需求描述用于确定梳理范围，不自动视为页面行为证据。

**⚠️ 输入护栏（防常识猜测，硬约束）**：
- 输入**必须**同时具备 ① 当前用户目标 ② 本轮 `explorer.md` 探索记录；**仅提供站点名称/URL 不足以启动本 Skill**。
- 若输入只有站点名/URL 而无探索记录 → **停止并提示先运行 `playwright-explorer-skill` 或提供 explorer.md**，不得用站点名、行业常识、通用模板推测业务功能/流程/字段/状态/权限。
- 业务功能、主流程、字段、状态、权限**只从 explorer.md 事实归纳**；`fact` 之外一律标 `inference`/`question`，不得升级为确定规则。

### 4. 知识基线
- Explorer 产物标准结构（输入契约）：`探索目标与环境` / `覆盖统计`+`增量轮次` / `已验证路径清单` / `页面与入口清单` / `探索记录(REC-xxx)` / `证据索引` / `疑点(Q)` / `仍未探索的缺口(G)`。梳理时按区段取数，不要只凭记忆或临时浏览。
- REC 字段与取值：`主张类型`（`fact`/`inference`/`question`）与 `证据状态`（`verified`/`candidate`/`blocked`/`contradicted`）；消费以 REC 原字段为准，不要凭页面文案猜测。
- 仅消费 `fact + verified` 作为确定事实；其余按「事实优先级与冲突处理」保留不确定性，不得升级为规则。
- 五类测试要素（字段/状态/权限/数据/环境）概念（用例优先级/就绪状态由下游 testcase-skill 判定）。

## 🚶 标准化工作流

### Step 1：环境预检（确认目标、输入与事实索引）
- 确定当前用户目标、业务功能/用户任务、feature、`PROJECT_DIR`，读取对应 Explorer 文件；若一个 Explorer 文件覆盖多个目标，限定本次范围并引用相关 REC。
- 建立事实索引：以 Explorer 的 `已验证路径清单` 为主入口，结合 `证据索引` 与 `站点地图`，按业务功能收集相关角色、进入条件、跨页面入口、用户动作、页面响应、业务对象及可观察状态变化，保留来源 REC 与证据状态；**不收集/不引用定位线索**。同步扫描 `疑点(Q)` 与 `缺口(G)`：疑点→「待确认问题」，缺口→补测清单候选。
- 确认探索记录的 `主张类型`/`证据状态` 取值：
  - `fact + verified`：已观察事实，用于梳理流程，不外推为普遍规则。
  - `fact + candidate`：候选事实，标注待确认，不得作为确定流程条件。
  - `inference`：可解释多页面事实如何组成用户任务，须写依据并标注为推理/候选；未确认前不能写成确定规则。
  - `question` / `blocked`：只用于指出未知或受阻，禁止推导未观察的页面响应/状态/权限规则。
  - `contradicted`：并列引用冲突证据，标注冲突未解决，不得自行选边。
  - 用户目标界定范围但不等于页面行为证据；需求与 Explorer 事实不一致时分别记录列为待确认。已明确保留的产品问题、授权阻塞或禁止动作，不要求停止已证实部分的梳理，在文档中保留原因与关联 REC，不猜测补齐。
  - 项目目录或 `spec/` 不存在时先创建；不得清理、移动、重命名或覆盖其他用户文件。

### Step 2：核心操作执行（还原主线 + 强制分支 + 五类测试要素 + 自动补测闭环）
1. **还原业务主线**：从探索记录中圈出一条与目标相关、动作连续且有测试价值的主线。每一步写明当前角色/进入条件、用户动作/页面响应、业务对象/状态变化、对应页面事实与未解决问题；可跨多页面组织成一项完整用户任务；未观察到的连接作为候选解释或待确认，不补造（**不绑定定位线索**）。
2. **梳理强制分支**：检查与主线相关的权限不足、必填为空/字段边界、数据不存在、业务状态限制、加载失败、依赖失败、重复提交、并发/竞态、角色差异及配置/环境差异。逐项说明是否进入后续设计及理由（见「强制分支的判断规则」）。
3. **检查五类测试要素与交接完整性**：检查字段、状态、权限、数据、环境是否有材料或明确缺口；输出风险和待确认问题（五类测试要素不是覆盖维度）。
4. **自动补测与分支就绪度判定**：对影响流程/分支判定的可补测缺口执行下节闭环；重新读取 Explorer 证据后才确定分支取舍。证据完整、动作获准且有明确可观察结果的连接标"进入后续设计"；证据不足或禁止/受阻的项标"不进入后续设计"并列入待确认，不得让下游猜测补齐。

**自动补测闭环**：当发现待确认问题、`question`/`candidate`/`blocked` 证据或缺少影响主流程/关键断言/场景就绪度的页面事实时（**不含定位线索**），默认在本轮**自动转入 `playwright-explorer-skill` 的增量探索流程**，而不是只把问题留给用户或 Generator：
1. **建立定向补测清单**：优先扫描 `疑点(Q)` 与 `缺口(G)`，挑出会改变流程步骤/分支/断言/场景状态且与目标相关的问题；逐项记录问题、关联 REC/步骤、所需观察、角色/初始状态及安全边界。与当前目标无关的缺口不触发补测（**定位线索不在补测范围**）。
2. **判定可执行性**：对照 Explorer 边界、项目资料和当前授权，区分只读/安全导航、可能持久化副作用、禁止动作和需额外认证的操作；不得把"补测"解释为扩大授权。
3. **自动运行 Explorer 增量探索**：对授权明确且可安全执行的问题，按 Explorer 规则先读原探索文件及缺口，只补测清单目标；复用当前已授权角色/会话，不重走无关的 `fact + verified` 路径。新事实由 Explorer 续接 REC 编号，写回同一 `explorer.md` 并更新地图/索引/缺口；不得创建第二份探索文件。
4. **遇到门槛时暂停对应项**：缺授权/账号、遇验证码或风险提示、需用户确认可能的副作用，或涉及明确禁止的写入/交易时，停止该项并请求必要授权/输入；无须中止其他安全独立的补测。无安全浏览器能力时明确记录无法执行，不得声称已补测。
5. **回读并核验**：Explorer 更新后重新读取原文件，核对新 REC 的角色/URL/动作/直接观察/状态变化与证据状态；只将 `fact + verified` 用作已确认事实，其他状态继续保留不确定性（**不核验定位线索**）。
6. **同步更新 Planner 文档**：在原 `business_flow.md` 中增量更新相关流程、强制分支、五类测试要素、风险、待确认问题；逐项引用新 REC，只调整被新证据支持的结论与分支取舍，保留未受影响内容，不另建版本，不默默删除缺口。
7. **完成判定**：本轮可安全补测的问题均已执行，或明确记录为 `BLOCKED`/仍需用户确认后才结束；列出已补测/未补测及原因，确保 Explorer 与 Planner 的 REC 引用一致。新证据产生的新的、与目标直接相关且可安全执行的问题可再做一轮定向补测；每个问题每轮只尝试一次，避免循环。

只有需产品决策、账号/权限补充或可能副作用授权时才询问用户；能通过授权内只读观察回答的应先自动补测，不把可由 Explorer 确认的页面事实转成用户确认问题。补测优先顺序：影响主流程连续性/关键分支判定的缺口 → 改变"进入后续设计"判定的缺口 → 相关权限/空态/异常分支。用户明确要求只规划不浏览、或当前会话不具备安全执行条件时，不触发浏览器操作，列明阻塞及下一步所需条件。

### Step 3：结果格式化（输出 business_flow.md）
输出保存为 `<PROJECT_DIR>/spec/business_flow.md`；若已存在先读取并增量补充，保留已有内容与来源，不覆盖已记录事实。本 Skill 唯一产物是业务流程文档（§1–§7）；**不生成测试用例、pytest 代码、页面对象或另一个探索记录**；文档含可交接的业务流与分支判定，用例设计由下游 `playwright-testcase-skill` 完成，不允许补造未观察的测试行为。

文档按以下结构编写（无证据支持的部分仍保留标题，并写明"待确认"及原因）：

## 3. 主流程
| 步骤 | 用户动作 | 页面响应 | 业务状态变化 | 来源事实（REC-xxx） | 证据状态/缺口 |

## 5. 五类测试要素（不是覆盖维度）

**强制分支的判断规则**：逐项考虑权限/字段/状态/数据/环境/异常/重复操作/并发竞态（仅当有证据或需求指出时）；不适用或无证据时也必须说明，不要为填表制造分支。每个分支须二选一：**进入后续设计**（与目标相关且证据足以支撑测试价值，注明证据范围与限制）或**不进入**（无关/禁止/缺证据，说明原因并将重要未知项列入待确认；禁止的交易/写操作说明风险边界但不得设计为执行性路径）。

## ⚠️ 约束与规范

### 1. 业务规范（证据与场景）
- 仅消费 `fact + verified` 为确定事实；`inference`/`question`/`candidate`/`blocked`/`contradicted` 保留不确定性，不得升级为规则。
- 业务流与强制分支以 REC 引用与可观察描述表达；**不绑定任何定位线索**（其由下游 Generator 获取）；若因定位困难有执行风险，相关分支标"不进入后续设计"并列入待确认，不在本阶段猜测或要求 Explorer 补采定位。
- 五类测试要素是材料清单，不是测试覆盖维度。

### 2. 安全边界
- 不读取或复制凭据；业务流程文档不含账号/密码/令牌/验证码/不必要个人信息。
- 不伪造或直接改写 REC；补测交由 Explorer 增量探索；不以临时浏览器观察替代 Explorer 补测；不自行访问站点代替 Explorer，也不新建/伪造探索记录。

### 3. 性能约束（补测循环防护）
- 每个补测问题每轮只尝试一次，避免循环或重复动作；无安全浏览器能力时明确记录无法执行，不得声称已补测。

### 4. 输出规范（唯一产物）
- 唯一产物为 `business_flow.md`；不生成 pytest 测试代码、页面对象或另一份探索记录；文档含可交接的业务流与分支判定但非自动化代码，不补造未观察行为。

## ✅ 验证与自查

### 1. 功能校验（质量门禁）
- 主流程含角色/进入条件/动作/页面响应/业务状态变化及来源事实；每步有 REC 或清楚标为待确认。
- 操作与结果以 REC 引用与可观察描述为主（不要求映射定位线索）；缺失步骤/线索已标明来源与影响。
- Explorer 证据状态未被升级；需求/观察/推断/问题/阻塞/冲突保持区分。
- 五类测试要素逐项给出已知内容或缺口；强制分支覆盖异常/重复操作/并发竞态，未观察行为明确列为待确认。
- 每个分支明确"进入后续设计"或"不进入"及原因；事实不足时先选"不进入"并将未知列入待确认。

### 2. 完整性校验
- 影响当前目标的可安全补测缺口已自动委派 Explorer 增量补测；探索记录与业务流程文档均已同步，或未执行项已注明授权/环境/安全阻塞原因。
- 每个强制分支均明确"进入后续设计"或"不进入"及理由；"进入"项可追溯至 REC 且有 `fact + verified` 支撑，"不进入"项原因合理且重要未知列入待确认；禁止的交易/写操作说明风险边界但不得设计为执行性路径。
- 五类测试要素逐项给出已知内容或明确缺口；无证据的类别已说明不适用原因，不为填表制造分支。
- 本阶段不产出场景级字段/优先级/就绪状态；用例级设计（测试点→场景、P0/P1/P2、READY 判定）由下游 `playwright-testcase-skill` 基于本业务流生成。

### 3. 常见错误排查
- 把需求陈述伪装成本轮观察，或把推断/常识写成确定规则。
- 把五类测试要素（字段/状态/权限/数据/环境）误称为测试覆盖维度。
- 为填表制造不存在的分支/并发竞态。
- 在业务流中绑定定位线索，或把"进入后续设计"的分支当作已就绪用例。
- 把可由 Explorer 确认的页面事实转成用户确认问题，而未先尝试授权内只读补测。

### 4. 最终确认（审核交接）
- 完成或增量更新 `business_flow.md` 后，必须调用 `playwright-plan-review-skill` 审核 Explorer 证据到 Planner 业务流的交接；未审核通过不得交下游。
- 若审核发现 Explorer 事实缺失/REC 不可追溯/与实时页面冲突，按其判定转交 `playwright-explorer-skill` 增量补测并追加 REC；回读后重跑 Planner 再交复审。
- 若审核发现流程串联/分支取舍/REC 引用与证据不一致，由 Planner 修订原文档并复审；不得为通过审核而提高 Explorer 证据等级。
- 未决项属于产品规则/用户决策/缺账号授权/禁止操作时按"不进入后续设计"保留并列入待确认；只要已证实流程可独立梳理，继续完成文档并交审核，不得以未决项替代整个业务梳理。
- 审核通过后才可交下游 `playwright-testcase-skill` 设计用例；保留审核报告指出的边界，并确保下游仅基于"进入后续设计=是"的分支与已证实事实设计用例。
